# 小游戏平台与研发路线

## 1. 平台策略

推荐顺序：

1. Web 内测版。
2. 微信小游戏。
3. 抖音小游戏。

原因：

- Web 内测最快，方便调玩法和数值。
- 微信小游戏用户路径短，适合社交传播和留存验证。
- 抖音小游戏适合内容分发和短视频传播，但平台适配和素材运营要求更高。

## 2. 小游戏约束

需要重点关注：

- 首包体积。
- 分包加载。
- 启动速度。
- 低端机性能。
- 资源压缩。
- 本地存储限制。
- 激励广告接入。
- 分享链路。
- 审核合规。

技术上要提前准备：

- 平台适配层。
- 分包资源结构。
- 离线可玩基础能力。
- 配置版本号。
- 存档迁移。
- 清除缓存。
- 日志和埋点。

## 3. 研发阶段

### 阶段一：Cocos 原型

目标：

- 跑通核心手感。

内容：

- 一个角色。
- 三个技能。
- 四种怪物。
- 一个 Boss 原型。
- 一张旧巷地图。
- 魂火、升级、结算。

验收：

- 30 秒内有爽感。
- 低端机 30 FPS。
- 能完整打一局。

### 阶段二：核心战斗框架

目标：

- 建立可扩展 runtime。

内容：

- EntityManager。
- ObjectPool。
- CollisionSystem。
- SkillSystem。
- SpawnSystem。
- BossSystem。
- DropSystem。
- ObjectiveSystem。

验收：

- 300 怪峰值可运行。
- 8 个技能可配置。
- 3 种关卡目标。
- Boss 有阶段。

### 阶段三：MVP 内容

目标：

- 形成可公开测试版本。

内容：

- 3 个角色。
- 12 个技能。
- 6 个进化。
- 20 种怪。
- 4 个 Boss。
- 3 个章节。
- 30 个关卡。
- 天赋、图鉴、剧情残页。

验收：

- 玩家可玩 30 到 60 分钟不明显重复。
- 每章有明确机制。
- 至少 3 种技能流派。

### 阶段四：微信小游戏

目标：

- 上线微信小游戏测试版。

内容：

- 微信构建。
- 分包。
- 平台存储。
- 分享。
- 激励广告。
- 基础埋点。
- 性能调试。

验收：

- 首包和资源结构符合平台要求。
- 启动速度可接受。
- 存档稳定。
- 广告奖励链路完整。

### 阶段五：留存与商业化

目标：

- 提升次留、七留和广告收益。

内容：

- 每日任务。
- 签到。
- 成就。
- 无尽夜行。
- 每日镇夜。
- 鬼市试炼。
- 更多角色和皮肤。

### 阶段六：抖音小游戏

目标：

- 接入抖音小游戏。

内容：

- 抖音构建。
- 平台 API 适配。
- 激励广告。
- 分享和录屏能力，后置。
- 抖音渠道数据埋点。

## 4. 人员拆分

最小团队：

- 1 名客户端主程。
- 1 名玩法/数值策划。
- 1 名 2D 美术。
- 1 名 UI/动效设计。
- 音频可外包或使用商用素材。

一个人做时的策略：

- 先用占位美术。
- 玩法手感优先。
- 配置系统尽早搭。
- 不急着商业化。
- 每周必须有可玩版本。

## 5. 主要风险

### 内容重复

表现：只是怪变多，玩法没变化。

解决：

- 每章加入独立机制。
- 怪物行为差异化。
- Boss 阶段机制化。
- 关卡目标组合化。

### 画面太乱

表现：看不清角色、怪、危险区域。

解决：

- 特效分层。
- 危险提示高优先级。
- 技能透明度控制。
- 低端机降级。

### 数值失控

表现：早期太难或后期碾压。

解决：

- 记录每关失败时间和死亡来源。
- 控制局外成长上限。
- 让局内构筑决定单局上限。

### 包体过大

表现：小游戏首包无法通过或启动慢。

解决：

- 首包只放第一章和基础资源。
- 后续章节分包。
- 音频压缩。
- 图集压缩。
- 剧情图后置加载。
